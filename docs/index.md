## Custom Project

### Dataset

The dataset used by my Kafka producer was the example sales.csv, which contains
sales transaction records.

Each record contains the following fields:

- order_id
- datetime
- region_id
- currency_code
- product_id
- unit_price
- quantity
- is_online
- customer_id
- is_new_customer
- device_type
- payment_method
- referral_source
- discount_code
- customer_note

I used the original sales dataset provided for the project and did not make any
changes to the source data. For validation and enrichment, I also used
regions.csv, products.csv, and discount_codes.csv as reference datasets.

### Data Contract

The data contract defined the rules each sales message had to follow before it
could be processed. Required fields included values such as the order ID,
product ID, region ID, quantity, and unit price. The discount code field was
optional. Product IDs and region IDs had to match values found in the reference
datasets. A message was considered valid if all required fields were present and
contained acceptable values. Messages that were missing required information or
contained invalid reference values were rejected.

### Kafka Messages

The producer sent sales transaction records to a Kafka topic one message at a
time. The Kafka topic was configured through the project's environment settings.
I used the region_id as the message key so sales from the same region would stay
grouped together. The original sales data was sent unchanged by the producer,
while the consumer added additional fields during processing.

### Consumer Validation

The consumer checked each incoming message against the data contract before
processing it. Required fields were validated, and reference values were checked
against the lookup datasets. If a message passed validation, it was enriched,
included in the running analytics, and written to the output CSV file. If a
message failed validation, it was rejected and excluded from the analytics. This
process helped ensure that only reliable data was used for reporting and
analysis.

### Data Engineering and Enrichment

The consumer generated several derived fields to make the data more useful.
These included:

- subtotal
- tax_amount
- total

Tax rates were obtained from the regions.csv reference file.

I also added two custom fields:

- discount_applied, which indicates whether a discount was used.
- discount_used, which shows the specific discount code used.

These additions make it possible to analyze how often discounts are used and
which promotions are most popular.

### Streaming Analytics

As messages were consumed, the application continuously updated running
statistics.

These included:

- Total Sales
- Average Sale Amount
- Minimum Sale Amount
- Maximum Sale Amount

I also added a feature that compares each sale to the current average and logs
whether the sale is above average or below average. This provided immediate
insight into how each transaction compared to overall sales performance.

### Experiments

For my Phase 4 enhancement, I added a comparison that determines
whether each sale is above or below the current average sale amount.

For my Phase 5 enhancement, I added the discount_applied and discount_used
fields. This allowed me to identify not only whether a discount was used, but
also which specific promotion was applied to each transaction.

### Results

The producer successfully generated and sent sales messages to Kafka, and the
consumer successfully processed them. Valid messages were accepted and written
to the output CSV file, while invalid messages were rejected according to the
data contract.

The output CSV contained both the original sales data and the derived fields
created by the consumer, including discount_applied and discount_used.

The logs displayed running sales statistics as well as messages indicating
whether individual sales were above or below the current average.

### Interpretation

This project helped me understand how important validation is in a streaming
data environment. By validating messages before processing them, the consumer
was able to prevent bad data from affecting the analytics results.

The biggest change I made was adding discount tracking. By including the
discount_applied and discount_used fields, I was able to gain additional insight
into customer purchasing behavior and promotional usage. This information could
help a business identify which discount programs are being used most frequently
and evaluate the effectiveness of different promotions.

The running statistics provided a current view of overall sales performance,
while the discount tracking added another layer of business intelligence that
could be used to support marketing and sales decisions.
